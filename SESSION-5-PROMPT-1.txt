PART 1: ALARM + VOICE ON THE CANCEL AFFORDANCE
- The escalation rules require, while an episode is in its cancel window (and during cascade until resolution), a LOUD alarm and a SPOKEN voice prompt telling the wearer what is happening and that tapping "I'm OK" cancels.
- Implement an alarm service behind an interface (e.g. lib/rehearsal/alarm_service.dart): start(), stop(), and a voice prompt method. Wire it into the interactive rehearsal: alarm starts when the episode triggers, stops immediately on wearer cancel, on kin ack, and at resolution; it never keeps sounding after RESOLVED.
- Real implementation: use a maintained Flutter audio plugin (audioplayers) for the alarm tone (bundled asset, generated tone file is fine) and flutter_tts for the voice prompt IF both resolve cleanly from pub.dev and pass analyze. If a plugin does not resolve or breaks the build, fall back to a platform-channel-free no-op implementation behind the same interface, clearly labelled in code and in the result file as not producing sound in this build. Do not fake it: the result file must state plainly whether real sound was actually produced anywhere (the VM has no audio device, so verification here is by interface, wiring, and tests, not by ear — say exactly that).
- Tests: a mock alarm service records start/stop/voice calls; widget/unit tests assert the alarm starts on trigger, stops on cancel-in-window, stops on mid-cascade cancel, stops on kin ack, stops at dispatch/resolution, and that the voice prompt text names the cancel action. No test may require a real audio device.

PART 2: CONSENT GRANTS + REVOCATION, ENFORCED
- Model: wearer-owned grants, per role (kin, provider, nutritionist) and per data class (alerts, vitals_digest, fhir_export). Defaults: no grants exist at first run (deny by default).
- Storage: in-app state with the same labelling honesty as the rest of the app (this build's grants are local demo state; say so on screen). Every grant and revocation is recorded in an append-only, hash-chained consent log (reuse the engine's EventLog approach or a small dedicated log with the same anchor/verify discipline), and the wearer can view that log in plain language ("You allowed Dr. — provider — to receive FHIR exports on Nov 17; you revoked it on Nov 18").
- UI: a Consent screen listing each role x data class with grant/revoke controls sized for the wearer (large touch targets, plain words, no jargon). Reachable from home without shrinking the two big buttons below the 120px floor (Session 3/4 layout lesson: use the compact destinations row pattern).
- Enforcement (this is the point of the part):
  a) FHIR export (Session 4): when there is no active provider fhir_export grant, the export action refuses with a clear on-screen reason and builds nothing. When the grant exists, export proceeds as before. When a grant is revoked, a later export refuses again. Tests cover all three states. (Session 4 disclosed this was unenforceable because grants did not exist; this session closes that gap, and the provider screen copy must be updated to match reality.)
  b) Kin alerts in the interactive rehearsal: when the kin alerts grant is absent or revoked, the cascade skips kin notification with a logged reason in the episode log (e.g. consent_not_granted) and proceeds by the canonical rules (the pass still exhausts to dispatch in simulation). The engine itself is not modified; enforce at the notifier boundary in the rehearsal layer, and log it so the timeline shows it honestly.
  c) Nutritionist role has no view yet (cut-line item); grants for it are modelled and shown in the Consent screen, labelled as having no active view in this build. Do not build the nutritionist view in this session.
- Tests: grant, revoke, re-grant flows; consent log chain verifies; export refusal/allow/refusal-after-revoke; cascade skip logging. Keep every prior test green.
